# VECO ASSETS — Roadmap V1

Développement par phases. Une phase n'est considérée terminée que si son critère de fin (section 11) est vérifié — on ne passe pas à la phase suivante si la phase courante ne fonctionne pas réellement (compilation, migrations, API, frontend, responsive).

## Phase 1 — Initialisation du projet *(terminée, backend non compilé faute d'accès Maven Central — voir section 13)*
- Structure `backend/` (Spring Boot, Maven, Java 21) et `frontend/` (Vite/React/TS).
- `docker-compose.yml` (postgres, backend, frontend), `.env.example`.
- Configuration de base (`application.yml`, Tailwind/shadcn, routing).
- Git initialisé, premier commit.
- README complet.
- Vérification : le backend démarre, le frontend démarre, `docker compose config` est valide.

## Phase 2 — Base de données *(terminée, migrations vérifiées à froid — voir section 13)*
- Migrations Flyway `V2`→`V9` pour l'ensemble des tables (sites/buildings/floors/zones/locations, roles/permissions/role_permissions/users/user_roles, asset_categories, asset_label_formats, assets, asset_assignments, asset_movements, asset_status_history, inventory_campaigns, inventory_scans, inventory_anomalies, asset_labels, attachments, audit_logs, settings) : PK/FK, index, contraintes uniques (dont partielles : numéro de série non dupliqué, affectation courante unique), contraintes `CHECK` pour les énumérations métier.
- 21 entités JPA correspondantes (`entity/`), relations mappées, deux classes de base (`BaseEntity`/`BaseCreatedEntity`) pour l'auditing `created_at`/`updated_at`, 21 repositories Spring Data (`repository/`), `AssetRepository` déjà `JpaSpecificationExecutor` pour les filtres combinables de la Phase 5.
- Seed de démonstration VECOPHARM (`db/seed/V900__seed_demo_data.sql`, profils `dev`/`demo` uniquement) : 5 sites avec hiérarchie de localisation complète, 7 catégories, 7 utilisateurs, 12 immobilisations réalistes.
- Vérification : migrations rejouées à froid sur PostgreSQL 16 vierge (V1→V9→seed), intégrité FK et contraintes métier (code/série uniques, énumérations, affectation courante unique) testées avec des insertions invalides qui échouent bien. Compilation Maven du backend **non vérifiable** dans l'environnement de développement utilisé (voir section 13) — à confirmer en priorité dans un environnement avec accès normal à Maven Central avant la Phase 3.

## Phase 3 — Authentification *(terminée côté code, non compilée/exécutée dans cet environnement — voir section 13)*
- `POST /api/auth/login` (JWT via `AuthenticationManager`/`CustomUserDetailsService`, autorités embarquées dans les claims), `GET /api/auth/me`, `JwtAuthenticationFilter` stateless, `SecurityConfig` avec `@EnableMethodSecurity`.
- `GlobalExceptionHandler` étendu (`AuthenticationException` → 401, message générique ne révélant jamais si l'email ou le mot de passe est en cause), `JsonAuthenticationEntryPoint`/`JsonAccessDeniedHandler` pour des 401/403 au format `ApiError` au niveau filtre.
- `GET /api/admin/audit-logs` (`@PreAuthorize("hasAuthority('ADMIN_ACCESS')")`) : première fonctionnalité réelle protégée par permission, sert de cas de test pour le critère de vérification ci-dessous (Administration > Audit, section 25/52 du prompt maître).
- Tests d'intégration (`AuthenticationIntegrationTest`) contre un vrai PostgreSQL 16 (Testcontainers, voir Phase 10) : login valide/invalide, `/me` avec/sans token, endpoint admin accepté pour `ADMIN` (a `ADMIN_ACCESS`) et refusé pour `CONSULTATION` (ne l'a pas) — rôles et permissions viennent des données de référence réelles de la Phase 2, pas de valeurs codées en dur dans le test.
- Vérification : restrictions d'accès testées par rôle/permission (backend, pas seulement frontend) — **test écrit et relu, non exécuté** dans cet environnement (ni Maven ni Docker/Testcontainers disponibles ici) ; à lancer en priorité sur un poste avec Docker avant la Phase 4.

## Phase 4 — Référentiel *(terminée côté code ; migrations et frontend vérifiés, backend Java non compilé par Maven dans cet environnement — voir section 13)*
- Backend : CRUD complet (créer/lister/modifier/désactiver-réactiver/supprimer) pour sites, bâtiments, étages, zones, localisations, catégories d'immobilisation et utilisateurs, avec les règles métier associées — unicité de code (globale pour les catégories, par parent pour la hiérarchie de localisation), suppression physique bloquée dès qu'une donnée est encore référencée (contrôle applicatif + `FOREIGN KEY ... ON DELETE RESTRICT` en base), aucune suppression physique de compte utilisateur (désactivation uniquement). Nouvelles permissions `REFERENTIEL_MANAGE`/`USER_MANAGE` (`V10__referentiel_permissions.sql`), nouvelle valeur d'audit `SUPPRESSION` distincte de `SUPPRESSION_LOGIQUE` (`V11__audit_action_suppression.sql`). `audit/AuditRecorder` généralise l'écriture de la piste d'audit pour ces 7 nouveaux services.
- Frontend : cette phase construit aussi ce que la Phase 3 avait laissé de côté côté client — page de connexion, restauration de session, intercepteur JWT/401 (`hooks/use-auth.tsx`, `routes/ProtectedRoute.tsx`) — sans quoi aucun écran d'administration n'aurait pu appeler l'API. Primitives shadcn/ui ajoutées à la main (`components/ui/`, faute d'accès réseau garanti au registre `shadcn`) : bouton, champ, select, dialogue, onglets, interrupteur, badge, case à cocher, formulaire (React Hook Form). Page `/sites` (onglets Sites/Bâtiments/Étages/Zones/Localisations/Catégories, un composant générique `LevelPanel` partagé par les 4 niveaux structurellement identiques) et page `/utilisateurs` (création/modification, affectation de rôles, changement de statut, réinitialisation de mot de passe) — tout provient de l'API, aucune valeur de référentiel codée en dur.
- Vérification : migrations V10/V11 rejouées à froid (permissions, contrainte `CHECK` étendue) et contraintes de suppression testées en conditions réelles (voir section 13) ; `npm run build` (tsc + vite) et `npm run lint` passent sans erreur sur le frontend Phase 4 ; aucune valeur de référentiel codée en dur côté frontend (confirmé par lecture du code : toutes les listes viennent de TanStack Query contre l'API réelle). Compilation Maven du backend **non vérifiable** dans cet environnement (voir section 13, inchangé depuis les Phases 1-3).

## Phase 5 — Immobilisations *(terminée côté code ; migrations/logique métier vérifiées à froid en SQL, frontend vérifié, backend Java non compilé par Maven dans cet environnement — voir section 13)*
- Backend : `AssetCodeGenerator` (composant dédié) génère le code (`nextval('asset_code_seq')` + `settings.asset_code.format`, repli sur `VECO-IMM-%06d` si le paramètre est absent/invalide — jamais de blocage de création pour un paramètre mal formé) ; `AssetSpecification` (`JpaSpecificationExecutor`, déjà câblé en Phase 2) pour les filtres combinables site/catégorie/état/statut/étiqueté/recherche texte ; `AssetService` avec liste paginée/filtrée/triée, création, modification et archivage (suppression logique uniquement, section 26). Toute modification de l'état physique ou du statut opérationnel écrit une ligne `AssetStatusHistory` (ancienne/nouvelle valeur) ; tout changement d'affectation (utilisateur courant, direction/département/service) clôt la ligne `AssetAssignment` courante et en ouvre une nouvelle — jamais un simple écrasement silencieux du champ. La chaîne de localisation (site→bâtiment→étage→zone→local) est validée par cohérence (un étage doit appartenir au bâtiment fourni, etc.), pas seulement par existence des identifiants. `AssetController` expose la liste, la fiche, l'historique d'état et l'historique d'affectation, la création, la modification et l'archivage, protégés par les permissions `IMMOBILISATION_VIEW`/`CREATE`/`EDIT`/`ARCHIVE` déjà seedées en Phase 2 (aucune nouvelle migration de permission nécessaire).
- Frontend : page `/immobilisations` (recherche, filtres combinables site/catégorie/état/statut, tri par colonne, pagination), formulaire de création/modification (`/immobilisations/nouveau`, `/immobilisations/:id/modifier`) avec sélection en cascade site→bâtiment→étage→zone→local, et fiche détaillée à onglets (`/immobilisations/:id`) : Résumé et Affectation/Historique branchés sur l'API réelle, Inventaire/Mouvements/Documents/Photos en placeholders honnêtes (Phases 6-8, même composant que les autres modules non encore construits — aucun appel API tant que le module n'existe pas).
- Génération automatique du code (`VECO-IMM-000001`, contrainte `UNIQUE` déjà en base depuis la Phase 2) — jamais saisi par l'utilisateur.
- Historique par immobilisation : changements d'état/statut (`AssetStatusHistory`) et affectations successives (`AssetAssignment`), tous deux consultables depuis la fiche.
- Point technique découvert et corrigé pendant la vérification SQL : l'ordre de flush par défaut d'Hibernate exécute les `INSERT` avant les `UPDATE` dans une même transaction, ce qui aurait pu violer l'index unique partiel `uq_asset_assignments_current` (au plus une affectation courante par immobilisation) en laissant momentanément deux lignes sans `assigned_until`. Corrigé en forçant un `saveAndFlush` sur la clôture de l'ancienne affectation avant l'ouverture de la nouvelle (`AssetService.closeCurrentAssignment`) — reproduit et vérifié directement en SQL (voir section 13).
- Vérification : parcours création → consultation → modification → historique simulé de bout en bout directement en SQL contre une base PostgreSQL 16 rejouée à froid (génération de code via la séquence, écriture d'historique d'état/statut, archivage logique, et le scénario de conflit d'affectation ci-dessus reproduit puis corrigé) ; `npm run build` et `npm run lint` passent sans erreur sur le frontend Phase 5.

## Phase 6 — Étiquetage *(terminée côté code ; migrations vérifiées à froid, frontend vérifié, backend Java non compilé par Maven dans cet environnement — voir section 13)*
- Backend : génération réelle de QR code (encode uniquement le code immobilisation, jamais une URL ni une donnée personnelle) et de code-barres Code128, via ZXing (`service/LabelImageGenerator`) — deux nouvelles dépendances Maven (`com.google.zxing:core`/`javase`, `org.apache.pdfbox:pdfbox`, licence Apache 2.0 comme le reste des dépendances) qui n'ont pas pu être résolues/compilées dans cet environnement (Maven Central bloqué, voir section 13), mais dont les coordonnées et l'API sont bien réelles, pas inventées. `service/LabelPdfBuilder` construit un vrai PDF avec Apache PDFBox — une page par immobilisation, aux dimensions réelles du format choisi (jamais une page A4 générique), logo/désignation/QR/code-barres positionnés proportionnellement selon les indicateurs du format. `service/AssetLabelService.generate(...)` valide le format (existe, actif) et les immobilisations (existent, non archivées), produit le PDF, puis pour chaque immobilisation : écrit une ligne `asset_labels`, passe `assets.labeled = true`, trace une entrée d'audit (`AuditAction.GENERATION_ETIQUETTE`, déjà prévue dans l'énumération depuis la Phase 3). `controller/LabelController` (`POST /api/labels/generate`, `GET /api/assets/{id}/labels`) et `controller/AssetLabelFormatController` (CRUD des formats, `GET /api/asset-label-formats`) complètent le module. `V12__etiquetage_permissions.sql` ajoute `ETIQUETTE_GENERATE` (ADMIN + GESTIONNAIRE_PATRIMOINE, même périmètre que la création/modification d'immobilisations) et `ETIQUETTE_MANAGE` (ADMIN seul, comme USER_MANAGE) — les tables `asset_label_formats`/`asset_labels` existaient déjà depuis la Phase 2, avec 3 formats de démonstration seedés.
- Frontend : nouvel onglet "Formats d'étiquette" dans `/sites` (Référentiel) pour administrer dimensions et contenu affiché (logo, désignation, QR code, code-barres), jamais codés en dur. Module `/etiquetage` : sélection multiple d'immobilisations (recherche, filtres site/catégorie, filtre "non étiquetées uniquement", sélection persistée à travers la pagination), choix du format, génération d'un vrai PDF renvoyé par le backend — prévisualisation (ouverture dans un nouvel onglet navigateur, le vrai PDF généré, pas une maquette) et téléchargement à partir du même fichier généré (une seule requête de génération, pas de double comptage dans l'historique).
- Vérification : `V12` rejouée à froid avec les 11 migrations précédentes et le seed (voir section 13) ; logique de génération simulée directement en SQL (écriture `asset_labels`, `assets.labeled = true`, entrée d'audit `GENERATION_ETIQUETTE` — valeur déjà valide dans la contrainte `CHECK` depuis la Phase 3) ; contrainte de suppression d'un format testée dans les deux sens (bloquée par `ON DELETE RESTRICT` quand un format est encore référencé par une étiquette générée, acceptée sinon) ; `npm run build` et `npm run lint` passent sans erreur sur le frontend Phase 6.

## Phase 7 — Inventaire *(terminée côté code ; logique métier vérifiée à froid en SQL — dont un bug réel trouvé et corrigé, frontend vérifié, backend Java non compilé par Maven dans cet environnement — voir section 13)*
- Backend : aucune nouvelle migration de schéma n'a été nécessaire — `inventory_campaigns`/`inventory_scans`/`inventory_anomalies` (Phase 2) et les permissions `INVENTAIRE_VIEW/CREATE/EXECUTE/VALIDATE` (déjà seedées et déjà réparties par rôle en Phase 2) existaient et n'attendaient que ce module pour être utilisées pour de vrai. `InventoryCampaignService.transition` fait progresser une campagne strictement d'une étape à la fois dans l'ordre `BROUILLON → EN_PREPARATION → EN_COURS → TERMINE → VALIDE → CLOTURE` (déclaré dans cet ordre dans `CampaignStatus`, jamais de saut ni de retour en arrière) ; faire progresser jusqu'à `TERMINE` est réservé à `INVENTAIRE_CREATE`, `VALIDE`/`CLOTURE` à `INVENTAIRE_VALIDATE` (séparation appliquée côté `InventoryCampaignController`, défense en profondeur même si seul GESTIONNAIRE_PATRIMOINE possède les deux aujourd'hui). `InventoryScanService.scan` implémente le parcours scan QR → vérification d'appartenance à la campagne → présence/anomalie (prompt maître section 15) : un code qui ne correspond à aucune immobilisation connue (ou à une immobilisation archivée) devient une anomalie `NON_REFERENCEE` sans ligne de scan (la FK `inventory_scans.asset_id` est `NOT NULL`) ; une immobilisation reconnue mais hors périmètre (site/zone) de la campagne devient une anomalie `MAUVAISE_LOCALISATION`, quel que soit le résultat demandé par le client ; sinon le scan est enregistré tel quel, avec création de l'anomalie liée si `résultat = ANOMALIE`. Règle explicite du prompt maître ("une campagne clôturée n'accepte plus de scans") appliquée en restreignant le scan aux campagnes `EN_COURS` uniquement — un sur-ensemble strict de l'exigence minimale, qui couvre aussi les statuts avant/après exécution. `InventoryAnomalyService` gère la consultation, le changement de statut (`NOUVELLE → EN_COURS → RESOLUE`/`REJETEE`, un statut terminal ne peut plus être modifié) et, nouveauté de cette phase, une vraie pièce jointe photo : `AttachmentStorageService` écrit le fichier sur disque (répertoire configurable `app.attachments.storage-dir`, volume Docker dédié) et `attachments` (table Phase 2, jamais utilisée jusqu'ici) en garde les métadonnées — première utilisation réelle de l'association polymorphe `owner_type`/`owner_id` du prompt maître section 47. `InventoryCampaignService.progress`/`pendingAssets` calculent la progression et les immobilisations restantes en croisant le périmètre réel (site, et zone si la campagne en cible une) avec les scans enregistrés, jamais un compteur stocké.
- Frontend : page `/inventaires` (liste filtrable par site/statut, création de campagne avec sélection en cascade site→bâtiment→étage→zone comme le formulaire immobilisation), page `/inventaires/:id` (en-tête avec progression en temps réel et barre de progression, boutons de transition de statut adaptés au statut courant et aux permissions, onglets Scanner/Anomalies/Historique des scans/Restantes). L'onglet Scanner est le cœur du parcours mobile : saisie du code (scan QR via douchette/caméra ou saisie manuelle — la caméra web n'a pas été implémentée dans cette phase, voir limite ci-dessous), bascule Présente/Anomalie, retour immédiat (toast) après chaque scan, champ ré-affiché et refocalisé pour enchaîner les scans sans naviguer. Page `/anomalies` (vue transverse toutes campagnes, changement de statut, galerie photo avec ajout). L'onglet "Inventaire" de la fiche immobilisation (`/immobilisations/:id`), placeholder honnête depuis la Phase 5, est maintenant branché sur l'historique réel de scan du bien.
- Limite assumée : le scan QR par caméra du navigateur (`getUserMedia`/lecteur de code-barres web) n'a pas été implémenté dans cette phase — le champ de saisie accepte aussi bien la frappe d'une douchette USB/Bluetooth configurée en "sortie clavier" (cas d'usage réel en entrepôt) que la saisie manuelle, mais pas encore une capture caméra en direct. À ajouter dans une itération dédiée si le matériel cible n'utilise pas de douchette.
- Vérification : parcours complet simulé directement en SQL contre une base PostgreSQL 16 rejouée à froid (campagne créée puis avancée jusqu'à `EN_COURS`, scan présent, scan anomalie avec immobilisation liée, code non reconnu, immobilisation hors périmètre, pièce jointe photo) — voir section 13 pour le détail, dont un bug réel trouvé et corrigé pendant cette vérification.

## 13. Limite connue de l'environnement de développement utilisé pour les Phases 1-7
L'environnement cloud dans lequel les Phases 1 à 6 ont été développées n'a pas accès à `repo.maven.apache.org` (bloqué par sa politique réseau) et n'a pas de démon Docker accessible. Conséquences :
- Le backend Java/Spring Boot n'a **jamais été compilé par Maven** dans cet environnement, phase après phase — le code a été relu attentivement à chaque phase (Phase 3 : signature JWT, wiring Spring Security, méthode par méthode ; Phase 4 : les 7 services CRUD référentiel/utilisateurs et leurs contrôleurs, méthode par méthode, plus un contrôle croisé systématique entre chaque nom de méthode de repository déclaré et chaque site d'appel dans les services ; Phase 5 : `AssetService`/`AssetCodeGenerator`/`AssetSpecification`/`AssetController`, même contrôle croisé méthode par méthode ; Phase 6 : `LabelImageGenerator`/`LabelPdfBuilder`/`AssetLabelService`, avec une attention particulière portée aux deux nouvelles dépendances externes — voir point dédié ci-dessous) mais `mvn compile` reste à exécuter dans un environnement avec accès réseau normal (poste de développement, CI Vecopharm) avant de considérer une phase backend entièrement close (voir section 11, point 2 "Compilation OK").
- **Risque propre à la Phase 6** : `pom.xml` ajoute deux dépendances externes (`com.google.zxing:core`/`javase` 3.5.3, `org.apache.pdfbox:pdfbox` 3.0.3) qui n'existaient pas avant — jusqu'ici, toutes les dépendances du projet venaient soit du BOM Spring Boot (versions déjà vérifiées), soit avaient un usage minimal (jjwt, springdoc). Ici, `LabelPdfBuilder` et `LabelImageGenerator` font un usage non trivial de l'API PDFBox 3.x (dont la signature de `PDType1Font` a changé entre PDFBox 2.x et 3.x — bascule vers `Standard14Fonts.FontName`) et de ZXing (`MultiFormatWriter`, `MatrixToImageWriter`). Les coordonnées Maven et les signatures utilisées sont réelles (issues de la documentation publique de ces bibliothèques, pas inventées), mais **n'ont pu être vérifiées par aucune compilation** dans cet environnement — c'est le point le plus incertain de tout le backend livré jusqu'ici, à vérifier en priorité par un `mvn compile` réel avant toute mise en production de ce module.
- Les migrations Flyway (Phases 2, 4 et 6) ont pu être vérifiées en conditions réelles (rejeu à froid contre un PostgreSQL 16 local, contraintes testées avec des insertions/suppressions invalides) car `psql` était disponible directement, indépendamment de Maven. La Phase 5 n'avait ajouté aucune nouvelle migration ; la Phase 6 en ajoute une seule (`V12__etiquetage_permissions.sql`, deux permissions) et s'appuie sinon sur les tables `asset_label_formats`/`asset_labels` déjà créées en Phase 2 — `V1`→`V12`→seed rejouée à froid avec succès, et la logique de génération d'étiquette (écriture `asset_labels`, passage de `assets.labeled` à `true`, entrée d'audit `GENERATION_ETIQUETTE`, contrainte de suppression d'un format référencé) **simulée directement en SQL** contre cette base, sur le même principe qu'en Phase 5 (voir ci-dessous pour ce précédent).
- Phase 5 (rappel) : aucune nouvelle migration (la table `assets`, la séquence `asset_code_seq` et les paramètres `asset_code.*` existent depuis la Phase 2/le seed) ; la logique métier de `AssetService` avait été simulée directement en SQL contre la même base rejouée à froid, ce qui avait permis de découvrir et corriger un risque réel d'ordonnancement Hibernate INSERT-avant-UPDATE sur `asset_assignments` (`saveAndFlush` explicite dans `AssetService.closeCurrentAssignment`).
- Les tests d'intégration (Phase 3 : `AuthenticationIntegrationTest`, basés sur Testcontainers pour utiliser un vrai PostgreSQL plutôt que H2 — voir Phase 10) n'ont en revanche **pas pu être exécutés du tout** ici : ils nécessitent à la fois Maven et un démon Docker, tous deux absents. Ils ont été écrits et relus avec la même rigueur, mais leur exécution réelle (`mvn test`) reste à faire dans un environnement normal. Les Phases 4 à 6 n'ajoutent pas de nouveaux tests d'intégration backend (aucun module de test supplémentaire n'a pu être exécuté ici de toute façon) ; les nouveaux services sont donc dans la même situation que le reste du backend — relus et vérifiés en SQL quand la logique le permettait, non compilés.
- Le frontend, lui, **a pu être vérifié pour de vrai depuis la Phase 4** : `npm run build` (`tsc -b && vite build`) et `npm run lint` (`oxlint`) passent tous les deux sans erreur sur l'ensemble du code (auth, primitives shadcn/ui ajoutées à la main, pages Référentiel/Utilisateurs en Phase 4, pages Immobilisations en Phase 5, formats d'étiquette et module `/etiquetage` en Phase 6, campagnes/scan/anomalies en Phase 7), le registre npm n'étant pas soumis à la même restriction que Maven Central. Ça ne prouve pas que les appels API fonctionnent contre un vrai backend démarré (non testé de bout en bout ici), seulement que le code TypeScript est correct et que le build de production réussit.
- **Phase 7 (rappel/particularité)** : contrairement à toutes les phases précédentes, la Phase 7 **n'ajoute aucune nouvelle migration Flyway** — `inventory_campaigns`/`inventory_scans`/`inventory_anomalies` (Phase 2) et les permissions `INVENTAIRE_VIEW/CREATE/EXECUTE/VALIDATE` (Phase 2, déjà réparties par rôle) existaient déjà et n'attendaient que ce module pour être utilisées pour de vrai — `V1`→`V12`→seed rejouée à froid sans aucun changement de schéma nécessaire. La logique métier (`InventoryCampaignService.transition`/`progress`/`pendingAssets`, `InventoryScanService.scan`, `InventoryAnomalyService.updateStatus`) a été **simulée directement en SQL** contre cette base, sur le même principe qu'en Phases 5 et 6, avec un parcours complet : création d'une campagne, transitions de statut valides et invalides (dont un test négatif confirmant qu'un saut d'étape est bien rejeté), scans d'immobilisations dans le périmètre, hors périmètre (anomalie `MAUVAISE_LOCALISATION` forcée) et d'un code inexistant (anomalie `NON_REFERENCEE` sans ligne de scan, la FK `inventory_scans.asset_id` étant `NOT NULL`), et vérification qu'une campagne `CLOTURE` refuse tout nouveau scan. Cette simulation a permis de découvrir et corriger un bug réel dans le calcul de progression : la première implémentation comptait comme "scannée" toute immobilisation ayant un scan pour la campagne, y compris les scans hors périmètre (`MAUVAISE_LOCALISATION`), ce qui pouvait afficher `remainingCount = 0` alors qu'une immobilisation du périmètre n'avait en réalité jamais été scannée — corrigé en calculant le périmètre réel (`scopeAssetIds`) côté Java et en croisant avec les identifiants scannés/présents par intersection d'ensembles, plutôt que par un `COUNT` SQL non filtré ; la correction a été revérifiée sur le même jeu de données (3 immobilisations en périmètre, 2 scannées + 1 scan hors périmètre → progression correcte à 2/3, la 3ᵉ bien listée par `pendingAssets`). Le stockage de fichiers (`AttachmentStorageService`, photos d'anomalie) est un stockage disque local réel (nommage UUID, répertoire configurable, protection contre la traversée de chemin) et n'a pas de dépendance Maven nouvelle à vérifier — seule l'API `MultipartFile`/`spring-web` déjà présente dans le BOM Spring Boot est utilisée.

Priorité pour la suite avant la Phase 8 : lancer `mvn compile`/`mvn test` (avec Docker) dans un environnement normal pour confirmer les Phases 2 à 7 côté backend — **en particulier la Phase 6** (ZXing/PDFBox, jamais compilées ici) — puis démarrer l'application complète (backend + frontend + PostgreSQL réels) pour vérifier de bout en bout le parcours connexion → Référentiel → Utilisateurs → Immobilisations → Étiquetage (génération d'un PDF réel) → Inventaire (création de campagne, scan réel via une douchette/lecteur QR ou saisie manuelle, déclaration d'anomalie avec photo, clôture de campagne).
